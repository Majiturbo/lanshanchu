# 阑珊处 · 产品案例

> 这是一份两三页的产品复盘，写给不了解这个项目的人：为什么做、怎么做取舍、实测了什么、下一步往哪走。完整需求文档见 [PRD（飞书）](https://my.feishu.cn/docx/AT09dTDmJoX9fax0NIacak76nyb)。

## 一、用户是谁（以及一个需要先说清楚的事实）

这份案例里的「用户」只有一个：**我本人**。

阑珊处是我在自用中长出来的产品——我每天要弄明白一些没弄懂的问题（技术选型、行业变化、某个说法到底靠不靠谱），发现通用 AI 给完一段答案就停了，下一问还得自己想。于是先做了给自己用的版本，边用边改。

因此需要说明：**项目目前没有外部用户访谈、问卷或客户反馈**。PRD 里所有「自测反馈」都是我使用时的记录，不是调研结论；二十余条调整记录整理在 [docs/iteration-log.md](iteration-log.md)。下文实测数字都标注了样本量，请在「n=1」的前提下阅读。

目标人群（尚未验证）：
- **主力画像**：做 AI、产品或技术工作的个人，一天多次要把一个问题彻底弄清楚，在意来源可核，反感重复组织提问。
- **相邻画像**：需要产出材料的知识工作者（咨询、运营、编辑），要的是可引用的结论与可复用的结构。

## 二、现有工具哪里不够

对比的是三类现实选择，不是某个具体竞品：

| 维度 | 通用 AI 问答 | 搜索引擎 + AI 摘要 | 笔记 / 知识管理工具 |
|---|---|---|---|
| 回答形态 | 单次对话，答案即终点 | 单次摘要 + 链接列表 | 用户自己录入整理 |
| 追问 | 用户自己想下一问 | 相关搜索推荐，链路常断 | 无 |
| 来源与时效 | 常无来源，或来源不可核 | 有链接，时间与权威性要自己判断 | 取决于用户录入 |
| 沉淀 | 会话历史，难成结构 | 无 | 手动组织 |

缺口是同一件事的三个面：**追问要自己想、来源要自己核、结构要自己建**。阑珊处只押一个点——把「一层层问到明白」变成默认路径：答案后给出带角度标签的延伸问题，点开即继续检索，逐层长成知识树。

## 三、四个关键取舍

1. **只接腾讯生态，不自建后端。**
   模型走 TokenHub、搜索走元宝搜索，密钥只在服务端，客户端经平台转发。代价是绑定单一供应商、必须登录；换来的是没有自建服务器、没有密钥泄露面、成本走按量账单。供应商抽象层保留扩展位，但换供应商要另做决策。

2. **自写 Agent 循环，不用 LangGraph / LangChain。**
   产品只有一条主链（研究循环 → 写答案）+ 少量输入框路由。框架会引入图状态、序列化与版本升级成本，收益不足以覆盖。改成自写的动作-观察循环：模型每步输出一个 JSON 动作，程序按注册表校验并执行，结果喂回同一段对话，带步数与时长预算兜底。
   重估条件：需要并行多分支 Agent、人工中断点或持久化执行图时。

3. **Tauri 同一套前端做多端，不另开 React Native 工程。**
   避免两套前端、两套交互与两次修 bug。代价是移动端手势、安全区、系统返回、软键盘都要自己处理（这一块的工程量在 PRD 的移动端适配一节里）。
   重估条件：移动端需要深度原生能力（后台常驻、系统级分享）。

4. **引用高亮用本地字重叠打分，不调模型判定。**
   每次角标都调模型判「这句是否支持结论」，成本与延迟不可接受。先用字二元组重叠在来源里找最相关的一句并高亮；**它只能说明「最相关的句子」，不能证明该句支持结论**。支持率靠抽样人工标注补，不假装已经解决。

另有一条与取舍相关的边界：历史、记忆、设置只存本机，不上传、不随账号走；提问内容、附图与检索资料会经平台转发给模型与搜索供应商，只用于生成这次回答。所以跨设备同步被列为非目标。

## 四、实测结果

### 4.1 线上 7 天真实使用（5 个账号，2026-10-30 至 11-06）

窗口 7 天，正式环境实际有调用的只有 11-02 至 11-05；5 个账号、16 台设备。来源是管理中心导出的埋点 CSV（930 行），下列数字与账号明细逐项对得上。

| 项目 | 实测 | 说明 |
|---|---|---|
| 调用 | 126 次 | 计费 105 + 不计费 21 |
| 计费拆分 | 105 次 | 回答 77、详解 8、总结 19、综合 1 |
| 不计费 | 21 次 | 输入框路由 10、记忆整理 11 |
| 模型调用 | 316 次 | 每次回答 4.10 次 |
| 搜索成功 | 332 次，退回 0 | 每次回答 4.31 次 |
| 额度消耗 | 542 单位 | 每次回答 7.04 单位 |
| 回答完成率 | 93.3% | 42 完成 / 45 尝试，失败 3（compose 2、quota 1） |
| 延伸问题点开 | 56.1% | 点开 23 / 出现 41 |
| 继续探索 | 87.5% 设备 | 漏斗 16 打开 → 7 建地图 → 8 拿到回答 → 7 继续 |
| 引用互动 | 看引用 83、打开来源 34、阅读视图 29 | 77 次回答 |
| 时延 | 中位 34.5 秒 | 提问到「回答完成」事件，含等待与阅读停留 |
| 卡点 | 登录失败 5、回答失败 3 | auth 5、compose 2、quota 1 |

三处口径先说清楚：①概览报 42 次完成、账号明细合计 77 次回答，前者是事件计数、后者才是扣额度的计费口径；②34.5 秒是端到端完成事件，与「生成耗时约 14 秒」不是同一个数；③这 5 个账号仍在自用圈内，不是外部用户。

### 4.2 成本：搜索侧已算，模型侧没有数据

搜索按元宝 SearchPro 20 元/千次：332 次 = 6.64 元/周，每次回答 0.086 元。按灯火约 95 次/月折算，搜索成本 8.2 元/月；月费若定 20–30 元，仅这一项就占 27%–41%。

模型侧算不出来：316 次调用没有 token 记录，账本只记次数，服务器上也没有能查 TokenHub 用量的密钥；三档月费未定，毛利同样空缺。要补齐只差两样：这一周该密钥的输入/输出/缓存 token（按小时才能套峰谷价），以及烛火、灯火、焰火的月费。

### 4.3 单项实测

全部为自测，标注样本量：

- **时延**：常规提问约 14 秒（DeepSeek Flash 主模型，2026-10-24，n=1）；换混元 Hy4 Preview 同一问题 76–92 秒。天气这类单一事实走快速路径后约 11.7 秒（规划 3.2 + 搜索 0.4 + 主模型 8）。
- **引用可定位率**：12 个引用角标中 10 个能在来源里定位到对应句子（83%，DeepSeek 话题，n=12，单一话题的单次抽样，只作初步观察、不作基线）；未命中的都是模型的抽象概括。用于系统评测的 30 题已在仓库 `eval/`，结果尚未跑。
- **卡片信息密度**：加长度与句式约束后，自动档平均从约 870 字降到约 470 字，简洁档从约 380 字降到约 180 字（同批来源各 5 题，2026-10-29），内容仍可读懂。
- **检索循环**：问「怎么养成早睡早起的习惯」，规划 3 个查询词约 3 秒、返回 12 条、复查判为常识类足够约 2.8 秒，研究阶段共约 6.4 秒；主模型整理答案约 60 秒（当时未加长度约束）。
- **埋点**：2026-10 起正式版有产品分析埋点（本地队列 → 平台，管理中心可看漏斗、事件次数、卡点与每人用量，可导出 CSV），不采集问题原文、答案与记忆全文。上表就是这套埋点导出的 7 天数据；**回答质量（引用支持率）仍无系统实测**。

## 五、下一步

1. **跑 30 题评测集**（已建在 `eval/questions.md`，单一事实 / 需理解 / 一句话多问各 10 题），每次改提示词或换模型都跑一遍，把引用可定位率与支持率做成基线。
2. **把单位经济算完**：搜索侧已闭环（0.086 元/回答）。剩下的两样拿到就能一次填满——该密钥一周的输入/输出/缓存 token、三档月费；模型侧在拿到 token 前不报任何数字。
3. **做 5–8 人任务观察**：30 分钟一次，看首次提问到第二层的完成率、卡点与放弃位置；这是把 n=1 的假设变成证据的最小动作。
4. **拆分文档**：PRD 保留用户行为、取舍与验收标准，把文件名、端口、能力配置等技术细节迁到独立技术设计文档。
5. 把产品案例的实测部分随每次评测更新，避免只剩目标值。
